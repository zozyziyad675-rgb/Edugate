💡 Why Linked Lists? (Array vs. Linked-List Model)

Array model: Elements are usually contiguous in memory. Indexing is O(1), but ordered insertion/deletion can require shifting many elements — that's O(n).

Linked-list model: Nodes can be allocated separately anywhere in memory. Logical order is created by references, not by physical position. End insertions can be O(1) when references are maintained.

Key idea: links define order; physical memory addresses do not need to be consecutive.

Engineering trade-off: Linked lists gain flexible relinking but lose O(1) random index access and add per-node reference overhead.

🧠 Analogy: An array is like seats in a row at the cinema — seat #5 is instantly found by counting. A linked list is like a treasure hunt: each clue (node) tells you where the next clue is. Finding the 5th clue means following 4 clues first!

---

🔗 Reference Model and Structural Invariants

Correctness depends on maintaining a few relationships after every update. Think of invariants as "laws" the list must never break.

Standard singly-list invariants:

· Empty: Head == null; Tail == null
· Non-empty: Head references the first node
· Tail references the last node (if maintained)
· Tail.Next == null in a non-circular list
· Count equals the number of reachable nodes

Trace variables: Head · Tail · current · previous · next

Debugging rule: after every mutation, check the invariants before moving to the next operation.

4.1 Singly Linked Lists — A One-Way Chain

Node anatomy: Each node contains:

· Data — the stored value
· Next — reference to the successor

The last node normally has Next = null.

Strengths: ✅ Dynamic growth ✅ O(1) AddFirst ✅ O(1) AddLast with Tail

Limitations: ❌ Sequential access ❌ O(n) search ❌ no natural backward traversal

---

💻 Node Representation in C# and Python

C# generic node:

public class Node<T>
{
    public T Data { get; set; }
    public Node<T> Next { get; set; }

    public Node(T data)
    {
        Data = data;
        Next = null;
    }
}
Python node:

class Node:
    def __init__(self, data):
        self.data = data
        self.next = None

class SinglyLinkedList:
    def __init__(self):
        self.head = None
        self.tail = None
        self.count = 0
⚠️ Crucial concept: Head stores a reference to the first node — not the whole list. The list "is" just a chain of references.

🥇 Insertion at the Head: AddFirst — O(1)

public void AddFirst(T value)
{
    var n = new Node<T>(value);
    n.Next = Head;
    Head = n;
    if (Tail == null) Tail = n;
    Count++;
}
Time: O(1) — a fixed number of link updates, no matter how long the list is.

Trace — insert 5 before 10 → 20 → 30:

Step Reference change
1 Create node 5
2 5.Next = old Head (10)
3 Head = 5
4 Tail stays 30

Empty-list boundary case: Before: Head = null, Tail = null. After AddFirst(x): Head = Tail = x.

This special case is why the Tail null check is required — without it, adding to an empty list would leave Tail stale.

---

➕ Insertion at the Tail: AddLast — O(1) with Tail

def add_last(self, value):
    n = Node(value)
    if self.head is None:
        self.head = self.tail = n
    else:
        self.tail.next = n
        self.tail = n
    self.count += 1
With Tail: O(1) ✅ — direct linking.
Without Tail: O(n) ❌ — must traverse to find the end.

Why Tail Matters — Complexity Trace

AddLast without Tail:

current = head
while current.next is not None:
    current = current.next
current.next = new_node
Operation count: List has n existing nodes. The while loop may move n-1 times, then one link is changed. Worst-case time: O(n).

---

🚶 Traversal Algorithm — Follow Next Until null

current = Head
while current != null:
    visit current.Data
    current = current.Next
Trace idea for 5 → 10 → 15:

· current = 5 → visit 5
· current = 10 → visit 10
· current = 15 → visit 15
· current = null → stop

Visit n nodes once → O(n) time | O(1) extra space.

🔍 Sequential Search and GetAt(index)

Linked lists do not provide direct random access!

Search by value:

def contains(self, target):
    current = self.head
    while current is not None:
        if current.data == target:
            return True
        current = current.next
    return False
Get by index:

current = head
for i in range(index):
    current = current.next
return current.data
· Search cases: Best O(1) (target at head) • Worst O(n) (target at tail or not found)
· Index access: Worst case near tail: O(n)

🗑️ Deletion Cases in a Singly Linked List

Correct code must handle structural boundaries. The six cases to test:

1. Empty list
2. Target is Head
3. Only one node exists
4. Target is in the middle
5. Target is Tail
6. Target is not found

Why predecessor matters: To remove a middle node X in a singly linked list, the predecessor must change its Next reference from X to X.Next. If only X is known, there is no Prev link to reach its predecessor directly. (That's a big reason doubly linked lists exist — Lesson 4.2!)

---

🧹 Remove(value) Algorithm — Search First, Then Relink

public bool Remove(T value)
{
    if (Head == null) return false;

    if (EqualityComparer<T>.Default.Equals(Head.Data, value))
    {
        Head = Head.Next;
        Count--;
        if (Head == null) Tail = null;
        return true;
    }

    Node<T> current = Head;
    while (current.Next != null &&
           !EqualityComparer<T>.Default.Equals(current.Next.Data, value))
        current = current.Next;

    if (current.Next == null) return false;

    if (current.Next == Tail) Tail = current;
    current.Next = current.Next.Next;
    Count--;
    return true;
}
Remove Head: O(1) | Remove by value: O(n) worst case.

Deletion Trace: Remove 15 from 5 → 10 → 15 → 20

Step current current.Next Action
1 5 10 10 is not target; move current
2 10 15 target found at current.Next
3 10 15 current.Next = current.Next.Next
4 10 20 final list: 5 → 10 → 20

Relinking is O(1); finding the predecessor may be O(n). This is the key cost separation the module emphasizes: search/location cost ≠ reference-relinking cost.

Deletion Edge Traces
· Remove Head (5 → 10 → 20): Head = Head.Next → Head becomes 10. If list becomes empty, Tail = null. Time: O(1)
· Remove Tail (5 → 10 → 20): Find predecessor 10 → 10.Next = null → Tail = 10. Worst case: O(n)
· One node: Before: Head = Tail = X. After removal: Head = Tail = null
· Not found: Search reaches null → return false → Count and links do not change

🐛 Common Singly Linked-List Bugs

Most failures are reference-state failures:

Frequent mistakes:

· Forget to update Tail after deleting the last node
· Overwrite a link before saving the remainder
· Dereference current.Next when current or Next is null
· Change Count after a failed operation
· Forget the empty/one-node case
· Create a cycle accidentally

Debug checklist:

· Draw nodes and arrows before the operation
· Write every reference change in order
· Check Head and Tail afterward
· Count reachable nodes
· Confirm Tail.Next == null
· Test with 0, 1, 2, and many nodes

🔄 Reverse a Singly Linked List In Place

Three references: prev, current, next.

def reverse(self):
    prev = None
    current = self.head
    self.tail = self.head      # old head becomes new tail

    while current is not None:
        nxt = current.next     # SAVE the remainder first!
        current.next = prev    # flip the link
        prev = current         # advance prev
        current = nxt          # advance current

    self.head = prev
O(n) time | O(1) extra space.

Reverse Trace: 10 → 20 → 30

Iteration prev current saved next Changed link
Start null 10 — —
1 10 20 20 10.Next = null
2 20 30 30 20.Next = 10
3 30 null null 30.Next = 20
End 30 null — Head = 30

Result: 30 → 20 → 10 → null; Tail becomes 10.

🧠 The golden rule of reversal: always save next before overwriting current.Next — otherwise you lose the rest of the list forever. That's mistake #2 on the bug list in action!

Lesson 4.2: Doubly Linked Lists — Full Lecture Walkthrough

Welcome back! In Lesson 4.1 we built a one-way chain where each node only knew its successor. Now we upgrade: every node will know both its successor and predecessor. This unlocks O(1) known-node deletion and natural backward traversal — but at a memory cost. Let's walk through every page, keeping all key terms in English.

---

🔗 Lesson 4.2: Doubly Linked Lists — Each Node Knows Both Directions

A doubly linked list is a chain where each node has two references, not one. This gives us natural forward and backward traversal — a huge benefit — but it comes with a cost: one extra reference per node and more link updates to maintain.

Node fields:

· Data — the stored value
· Next → successor (the node after it)
· Prev → predecessor (the node before it)

Lab alignment: Lab 5 introduces bidirectional navigation and invariant checks.
🧠 Analogy: A singly linked list is a one-way street — you can only drive forward. A doubly linked list is a two-way street — you can drive back and forth freely, but the road costs twice as much to build!

---

💻 Node Representation: Next and Prev Must Agree

C# DNode:

public class DNode<T>
{
    public T Data { get; set; }
    public DNode<T>? Next { get; set; }
    public DNode<T>? Prev { get; set; }

    public DNode(T data)
    {
        Data = data;
    }
}
Python DNode:

class DNode:
    def __init__(self, data):
        self.data = data
        self.next = None
        self.prev = None
⚠️ The core invariant of a doubly linked list: Next and Prev must agree. If A.Next == B, then B.Prev must equal A. Break this agreement and the list is corrupted.

---

➕ Doubly Linked Insertion — Insert After a Known Node in O(1)

The recipe for inserting after a known node:

1. New.Prev = left node
2. New.Next = right node
3. Right.Prev = New (if right exists)
4. Left.Next = New
5. Update Tail if insertion is after old Tail

def insert_after(node, value):
    n = DNode(value)
    n.prev = node
    n.next = node.next

    if node.next is not None:
        node.next.prev = n

    node.next = n
    return n
Known node: O(1) | Search-then-insert: O(n).

🔍 Trace: Insert 25 After Node 20 in 10 ↔ 20 ↔ 30

Step Reference update
1 25.Prev = 20
2 25.Next = 30
3 30.Prev = 25
4 20.Next = 25

Result: 10 ↔ 20 ↔ 25 ↔ 30

Invariant check (always do this after mutation!):

· 20.Next == 25 ✅
· 25.Prev == 20 ✅
· 25.Next == 30 ✅
· 30.Prev == 25 ✅

🧠 Order matters! Note that we set 25.Next = 30 before overwriting 20.Next. If we overwrote 20.Next first, we'd lose our reference to 30 and the rest of the list — the classic "save the remainder first" rule from Lesson 4.1!

---

🗑️ Delete a Known Doubly Linked Node — Local Relinking

Because each node has a Prev, we can unlink a known node without searching for its predecessor. This is the doubly linked list's superpower!

public void RemoveNode(DNode<T> node)
{
    if (node.Prev != null)
        node.Prev.Next = node.Next;
    else
        Head = node.Next;          // node was Head

    if (node.Next != null)
        node.Next.Prev = node.Prev;
    else
        Tail = node.Prev;          // node was Tail

    Count--;
}
📊 Complexity Distinction (very important for exams!)

· Known interior node: O(1) unlinking
· Known Head/Tail: O(1)
· Remove by value: search O(n) + unlink O(1)
· Total Remove(value): O(n) — search dominates

⚠️ Exam rule: Do not claim O(1) deletion unless you state how the node or predecessor is obtained. The O(1) is for the unlinking, not for finding the node.

Lab alignment: Lab 6 combines doubly linked deletion with a browser-history project.

🔍 Trace: Delete 20 from 10 ↔ 20 ↔ 30

Step Update
1 20.Prev is 10 → set 10.Next = 30
2 20.Next is 30 → set 30.Prev = 10
3 20 is detached from the list

Result: 10 ↔ 30

Boundary: remove Head

Head = oldHead.Next, then new Head.Prev = null

Boundary: remove Tail

Tail = oldTail.Prev, then new Tail.Next = null

🚶 Forward and Reverse Traversal — Same Asymptotic Cost

Forward:

current = head
while current is not None:
    print(current.data)
    current = current.next
Reverse:

current = tail
while current is not None:
    print(current.data)
    current = current.prev
Forward O(n) | Reverse O(n) — both are one clean pass.

Practical meaning: Prev supports browser Back, undo/redo navigation, and bidirectional iteration. This is exactly why browsers use doubly linked lists for history!

---

⚠️ Why Naive Singly Reverse Traversal Can Be O(n²)

Here's a beautiful complexity trap. In a singly linked list, to move backward you must re-find the predecessor each time — starting from Head:

curr = Tail
while curr != Head:
    prev = Head
    while prev.Next != curr:    # search from the start EVERY time
        prev = prev.Next
    visit curr
    curr = prev
visit Head
Cost reasoning:

· For many current nodes, predecessor search starts at Head
· One predecessor search can be O(n)
· Repeated for many nodes → O(n²)

Doubly list: curr = curr.Prev → one pass O(n).

Extra Prev memory buys simpler and faster backward traversal. This is the classic space-time trade-off: spend one extra reference per node, save an entire factor of n in backward traversal.

Lesson 4.3: Circular & Sentinel Variations

🔄 Circular Singly Linked Lists — The Last Node Links Back to the First

In a circular singly linked list, the last node's Next points back to Head instead of null.

Invariant: If non-empty: Tail.Next == Head

Natural uses: round-robin scheduling • repeating playlists • turn-based games • cyclic menus

🛑 Circular Traversal and Stopping Conditions

A loop must know when one complete cycle has finished:

def print_circular(head):
    if head is None:
        return

    current = head
    while True:
        print(current.data)
        current = current.next
        if current == head:
            break
Safe stopping strategies:

· Stop when current returns to Head
· Or traverse exactly Count nodes
· Do not rely on current == null in a healthy cycle — it never becomes null!
· Handle empty list before entering the cycle

⚠️ This is the #1 circular-list bug: writing while current != null — which loops forever, because a circular list has no null!

🔍 Circular AddLast Trace: Insert 40 into 10 → 20 → 30 → back to 10

Step Update
1 new = 40
2 40.Next = Head (10)
3 old Tail (30).Next = 40
4 Tail = 40

Invariant: Tail.Next == Head ✅ (40.Next == 10)

Head + Tail maintained → O(1) AddLast.

Lab alignment: Lab 7 implements circular insertion and traversal before the round-robin scheduler.

⏱️ Project: Round-Robin Scheduler

A circular structure models repeated turns naturally.

Simplified model:

· Each node stores a task/process name
· Current points to the active task
· After a time slice: current = current.Next
· New tasks can be inserted at Tail
· Finished tasks are removed from the cycle

Required lab tests:

· Empty scheduler
· One task loops to itself
· Three tasks rotate for multiple rounds
· Remove current Head/Tail
· Verify cycle invariant after each update

🧠 This is exactly how an operating system's round-robin CPU scheduler works! Each process gets a time slice, then the "pointer" moves to the next process — and after the last one, it wraps back to the first.

🔄 Circular Doubly Linked Lists

Each node has both Next and Prev, and both wrap around. Here, the last node's Next points to Head, and Head's Prev points to the last node.

Use case: photo gallery or cyclic navigation where both Previous and Next wrap around. Swiping left at the first photo takes you to the last one, and vice versa!

🔍 One-Node Circular Case and Deletion

The smallest valid cycle is a self-loop:

head = tail = newNode
newNode.next = newNode
newNode.prev = newNode
Remove the only node:

If Head == Tail and that node is removed:
Head = null, Tail = null
Do not leave stale self-references as the logical list state.

Boundary checklist: empty • one-node • remove Head • remove Tail • remove middle • preserve wrap-around links

Lab alignment: Lab 8 begins with circular doubly-list edge cases before sentinel nodes.

🛡️ Sentinel (Dummy) Nodes — Permanent Structural Nodes

Sentinels are permanent structural nodes that simplify boundary logic. Think of them as "guards" that always exist, so you never have to handle a missing neighbor.

Without sentinels (the painful way):

· Head may be null
· Deleting first node needs a special case
· Tail deletion may need a special case
· Empty and non-empty code paths differ

With Header + Trailer (the elegant way):

· Header and Trailer always exist
· First real node always has a predecessor
· Last real node always has a successor
· Many insert/delete operations share one uniform pattern

⚠️ Important: Sentinels simplify control flow — they do not make search O(1). You still must walk the list to find a value.

🔧 Uniform Local Operations Between Known Neighbors

Insert between left and right:

new.prev = left
new.next = right
left.next = new
right.prev = new
Delete a known real node:

node.prev.next = node.next
node.next.prev = node.prev
🔍 Sentinel Traces: Header (H) ↔ 10 ↔ 20 ↔ 30 ↔ Trailer (T)

Delete 10:

1. node = 10
2. H.Next = 20
3. 20.Prev = H
4. No special "delete first real node" branch! ✅

Insert 5 before 10:

1. left = H, right = 10
2. 5.Prev = H
3. 5.Next = 10
4. H.Next = 5
5. 10.Prev = 5

Notice how the same code handles "insert at front" and "insert in the middle" — no if Head == null branches anywhere. That's the sentinel magic!

Lesson 4.4: Arrays vs. Linked Lists — Select Structures by Workload, Not by Habit

📊 The Comparison Table

---

🏎️ Cache Locality and Memory Overhead

Big-O is necessary but not the whole performance story.

Arrays: locality advantage

· Elements are stored close together
· Sequential traversal often benefits from processor cache and prefetch behavior
· Per-element storage is compact

Linked lists: pointer overhead

· Nodes may be scattered in memory
· Traversal follows references and can incur more cache misses
· Each node stores one or two references plus object metadata

Two traversals can both be O(n) and still have different measured times. This is why benchmarking matters — Big-O tells you the growth rate, not the constant factor.

🧠 Analogy: Walking through a row of books on one shelf (array) vs. following a trail of notes scattered across a library (linked list). Both visit the same number of books, but the scattered version has more "walking time" between them — that's the cache miss.

🎯 Choosing the Right Structure — Decision Questions & Scenarios

Decision questions:

· Need O(1) random access by index?
· Where do insertions/deletions occur?
· Do I already have the node reference?
· Need backward traversal?
· Is memory overhead important?
· Will cache locality matter?
· Is size known or stable?

Scenarios (worked answers):

1. One million numbers, frequent index reads, rare inserts → array/dynamic array ✅ (O(1) index access wins)
2. Frequent front/tail changes, no random index access → linked structure ✅
3. Next/Previous navigation → doubly linked list ✅
4. Repeated cyclic turns → circular list ✅

🧠 Final Takeaway

Linked lists trade direct indexing and locality for flexible reference-based updates. Correctness depends on preserving structural invariants after every operation.

Let's recap the whole journey in one picture:

Structure Superpower Price
Array O(1) index access, cache locality O(n) shifts on insert/delete
Singly linked O(1) front insert/delete, dynamic no backward traversal, O(n) search
Doubly linked O(1) known-node unlink, backward traversal extra Prev reference + more link updates
Circular natural cyclic rotation must handle stopping conditions carefully
Sentinel uniform code, no boundary special cases two extra dummy nodes

Every design choice in this module is the same trade-off in different clothing: flexible relinking vs. fast direct access. When you face an exam question or a real project, ask the decision questions, check the invariants, and always state the precondition behind any O(1) claim.
